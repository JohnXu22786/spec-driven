# 立规（Spec）

## 本技能解决什么

规格是给 agent 的法律。代码可以重写，规格含糊导致的返工无法追责。
本技能规定规格的写法、质量标准与门禁：规格不合格，禁止进入实现。

## 规格五要素

规格书必须包含以下小节，顺序固定（微任务变体 spec.minimal 可省略「需求」小节，
审查引擎对此不拦门禁：小节缺失时无发现，小节存在但为空时仅 KEEL-0205 警告）：

1. **目标** —— 一段可验证的陈述（继承锚定阶段的「目标」）；
2. **边界** —— 「范围内」与「范围外」两个列表；范围外必须至少有一项；
3. **需求** —— 编号条目（R-01、R-02……），每条一个行为，禁止合并句；
4. **验收标准** —— 编号条目（AC-01、AC-02……），每条一个可验证结果；
5. **验证方法** —— 达成验收标准的具体手段（命令、测试用例、人工步骤）。

## 写法铁律

- 每条需求与验收标准只描述一个行为，出现「以及、同时」就拆开；
- 数字优先：用「3 秒内」「1000 条记录」代替「尽快」「大量」；
- 禁用范围蔓延措辞：「顺便、顺手、以后再加、如果时间允许」；
- 不在规格里写实现方案：规格回答「做什么」，实现方案属于规划阶段；
- 不确定的前提不写进正文：记入假设登记表（ASSUMPTIONS.md），由 keel-probe 处理。

## 工作流程

1. 调用工具 `keel_catalog` 确认模板可用；
2. 按任务规模选择模板（见 keel-anchor 的规模表），调用 `keel_spec` 生成规格书；
3. 逐项填写 fields；任何一项填不出，回到 keel-anchor 继续收敛；
4. 调用 `keel_review` 审查生成的规格书；
5. 修复全部错误；警告逐条判断：是真歧义就改规格，是误报就忽略。

## 门禁

- 规格书存在 error 级发现 → 未合格，禁止进入建造；
- 规格书合格但存在 warning → 允许进入建造，但每个 warning 都要有明确结论
  （已修改 / 判定为误报并说明理由）；
- 规格书合格且无 warning → 规格冻结，后续变更一律走变更单（change-request 模板）。

## 常见错误

- 把验收标准写成需求：需求描述行为，验收标准描述如何判断行为正确；
- 用「支持 XX 功能」当验收标准：验收标准必须可观察、可执行；
- 规格写完不审查直接实现：门禁的意义在于实现前发现，而不是实现后追认。
